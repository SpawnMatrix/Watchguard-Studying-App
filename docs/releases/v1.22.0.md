# Version 1.22.0 — An ideas board where anonymous means anonymous to us

Learners can post an idea, anonymously or under their username. An
administrator publishes, re-files or declines it with an optional reply, and
the result is a public board that doubles as a roadmap.

The interesting part is not the board. It is that "anonymous" here means
anonymous to whoever runs the server, not just to other learners — and that
replies still reach the person who asked.

## The problem those two requirements create

Routing a reply back to somebody normally means recording who they are. Every
obvious design stores an account id on the post and hides it in the interface,
which makes "anonymous" a display rule that anyone with database access can
undo.

So the post carries no author at all. Posting returns a random **claim**; the
author's browser keeps it, and the server stores only its SHA-256. To see what
happened to their ideas a browser presents the claims it holds, and the server
answers for exactly those. The lookup runs only in the direction the author can
drive — there is no query that goes from a person to their posts, because there
is no column to join on.

```sql
CREATE TABLE IF NOT EXISTS suggestions (
  id INTEGER PRIMARY KEY, body TEXT NOT NULL, display_name TEXT,
  claim_hash TEXT NOT NULL UNIQUE, status TEXT NOT NULL DEFAULT 'pending',
  admin_reply TEXT, created_at INTEGER NOT NULL, updated_at INTEGER NOT NULL);
```

`suggestions.test.ts` asserts that exact column list and fails if `account_id`,
`user_id`, `username`, `ip` or `session` ever appears — and scans the board's
own source for the same reaching. A behavioural test would pass a future edit
that added the column and simply did not exercise it.

## What it costs, said out loud

- **Clearing browser storage loses the thread.** The post stays; nothing can
  reconnect it to its author, us included. The posting form says so in plain
  words before anyone writes anything, next to a warning to leave personal
  details out.
- **Posting needs a signed-in learner.** The session is a spam control, checked
  and then discarded: the server authenticates somebody it then declines to
  record. Anyone using "Study on this device only" can read the board but not
  post.
- **A signed post carries the session's username**, never a name from the
  request body. Verified against a request that asked to be signed `chief`
  while holding `learner_one`'s session — it was signed `learner_one`.
- **`created_at` is not hidden.** Nothing else in the app records when a given
  person was active and there is no request log, so there is nothing to
  correlate it against — but it is not cryptographically prevented, and an
  operator who added a proxy access log could rebuild it. Same edge already
  noted for logs.

## Moderation is a second administrative capability

Worth naming as one. Until now the only thing an administrator could do about
another person was help them back into their account; reading a queue of things
people wrote is a different kind of power.

What it shows is bounded by the schema rather than the interface: the text, and
a name only where its author attached one. The admin API does not return the
claim either, so an administrator cannot impersonate an author to the server.

Declining hides a post from the board without deleting it, and its author still
sees it with that status. Withdrawing is the author's own action, guarded on
the claim, and is the only deletion on the board.

`docs/privacy.md` gains a section for all of this and the README a summary,
because a capability that is not written down is one nobody can check.

## A bug worth recording

The first version of the board paired every one of a browser's own posts with
whichever claim came back first, so **Withdraw would have deleted the wrong
idea.** The server knew which claim matched which row and was throwing that
away. It now returns the claim alongside each post — the caller supplied it, so
echoing it reveals nothing, and without it a client genuinely cannot tell its
own posts apart.

Caught by reading the code back rather than by a test, which is worth admitting:
every test passed, because they all checked ids the test itself already knew.

## Verification

- `npx vitest run` — 40 files, **358 tests**, green. `npm run lint`,
  `npm run build`, `check-release.mjs origin/main` at 1.22.0.
- 18 new tests: the schema guarantee, the source scan, claim pairing, guesses
  returning nothing, the bulk-lookup cap, withdraw-by-claim, moderation
  transitions, reply retention, the body and reply bounds, and the HTTP surface
  including cross-site refusal.
- Driven end to end in a production build on a scratch database: posted without
  a session (401), registered and posted anonymously, posted signed while
  trying to spoof the name, confirmed pairing and that a guessed claim returns
  nothing, confirmed the board stays empty until published, published one from
  the admin console with a reply, confirmed the waiting count fell from 4 to 3,
  and confirmed the reply reached both the board and the author.
- `lazySection.test.tsx` pinned the number of lazily-loaded sections at 7, so
  an eighth failed it. That count was never the property being protected — the
  next line already catches a lazy import bypassing `loadSection`. It now
  asserts every `lazy(` call goes through `loadSection`, with a floor.
- No Docker on this machine; CI's container job covers the image.

## Not in this release

One admin reply per idea, not a thread. Adding a `suggestion_replies` table
later is straightforward; a back-and-forth was more than this needed to be
useful, and every extra field is another thing stored about a conversation.
