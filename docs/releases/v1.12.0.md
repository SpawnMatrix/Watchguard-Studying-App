# Version 1.12.0 — Faster study: keyboard answers, sections in the URL, a lighter first load

A study session is the same few actions hundreds of times: read, choose, check, next. This release makes those actions quicker and stops the app from losing your place.

## Answer quiz questions from the keyboard

- **Choose:** press `1`–`9`, or the letter shown beside an option (`A`–`D`).
- **Check:** press `Enter`. Press `Enter` again for the next question.
- **Mouse and keyboard together:** click an option, then press `Enter` to check it. Before, Enter on the option you had just clicked un-chose it.
- **What stays the same:**
  - Once an answer is checked, keys can't change it.
  - A focused button handles its own Enter, so an answer is never checked twice.
  - Keys do nothing while you type in a field, or with Ctrl, Cmd or Alt held, so browser shortcuts keep working.
- **Other question types:** diagram, log and ordering questions keep their own controls, but Enter still checks and moves on.

A short hint under each question lists the keys. It is hidden on touch screens.

## Flip through flashcards with the arrow keys

The left and right arrow keys move to the previous and next card.

## Your section is in the address bar

The open section is now part of the URL, for example `…/#labs` or `…/#quiz`:

- **Reload** and you stay in the same section instead of returning to Study Home.
- **Back and Forward** move between the sections you opened.
- **Bookmarks and shared links** open the section they point to.

The "Skip to study content" link still works and doesn't change the section.

## A lighter first load

Before, the first visit downloaded every section at once: the lab simulator, the network sandbox, the quiz and the question bank, in a single 1.2 MB script. Now Study Home loads first, and each other section downloads the first time you open it. The first script is about 410 KB. A short "Loading section…" message covers the brief wait.

### Safe across deploys

The site redeploys whenever a change is merged, and each deploy replaces these files. Without extra handling, a tab opened before a deploy would ask for a file that no longer exists, and the whole app would go blank.

- **After a deploy:** the tab reloads once onto the new version and opens the section you asked for.
- **Remembering the reload:** the tab records which build it reloaded from. If the reload brings back that same build, no deploy explains the failure, for example when you're offline, so it doesn't reload again.
- **If a section still can't load:** that section shows "This section didn't load" with a **Reload the page** button, and the rest of the app keeps working. A section that fails while rendering is now contained the same way instead of blanking the page.

## Verification

- **Tests:** the new pure shortcut logic covers choosing by number and letter, keys past the last option, Enter before and after checking, modifier keys, typing in fields, focused buttons, Enter on a chosen option, and reading sections from the hash. Wiring tests confirm the quiz, flashcards and app use them.
- **Played through in the browser:**
  - opening `#labs` directly
  - switching to Flashcards, then Back and Forward
  - the skip link
  - arrow keys moving through the deck
  - choosing with `C`, then checking and advancing with Enter
  - clicking an option with the mouse, then pressing Enter, which checked it and recorded exactly one attempt
- **Deploy handling tests:** a successful load, one reload for a replaced file, no second reload on the same build however long it takes, a reload for a later deploy, no reload when it can't be remembered, the error panel, and that all seven sections use both.
- **Against the production build:**
  - **A real rebuild:** a tab on the old build opened Flashcards, reloaded once onto the new build, and showed the deck.
  - **A missing file with no deploy:** the tab reloaded once, then showed the error panel with no further reloads, and other sections still opened.
- `npm run lint` is clean, 287 tests pass across 32 files, and the build splits into per-section chunks.

No server, database or deployment change is required.
