# Version 1.18.0 — Close the recovery timing oracle and bound what the tutor forwards

Second of three in the privacy pass. 1.17.0 wrote down what the app records;
this one fixes what the inventory found.

## Recovery told you which usernames existed

`POST /api/account/recover` derived a key only when the account was real:

```ts
const attempted = typeof code === 'string' && code.length <= 100 && user
  ? await deriveSecret(trimmed, user.recovery_salt ?? '', user.recovery_kdf || 'sha256')
  : '';
```

An invented username fell through to `''` and came back in about a
millisecond. A real one paid a full scrypt derivation, around a hundred. The
response bodies were already identical — `Username or recovery code did not
match.` either way — but the time was not, so anyone with a list of names could
ask the portal which of them had accounts, without a valid recovery code and as
fast as the throttle allows. `login()` never had this problem: it hashes
against a stand-in salt whichever way it goes.

Recovery now does the same, with one wrinkle worth spelling out. An account
still carrying the legacy unsalted SHA-256 recovery scheme verifies instantly,
so simply always deriving "the account's own scheme" would reproduce the oracle
in reverse — a fast answer would mean an old but real account. Instead every
path pays exactly one current-scheme derivation:

- absent account: one scrypt against the stand-in salt,
- legacy account: a SHA-256 verification plus the same scrypt floor,
- current account: its own scrypt, and no extra.

`server/leaks.test.ts` compares medians of three and fails if the two diverge.
Removing the cost floor makes it fail; it was checked that way rather than
assumed.

## Tutor routes: what can be forwarded, and who can ask

`/api/lab/diagnostic` had no input validation at all — the 1mb body limit was
its only ceiling, and everything it received went to Google. The
`/api/quiz/evaluate` branch that forwards a question the catalogue does not
contain had the same gap, and that branch is the entire abuse surface of the
quiz endpoint: no ordinary client reaches it, because the server grades from
its own catalogue and returns its own explanation.

`server/tutorInput.ts` now caps every field on both. The caps sit at roughly
four times the largest real content in the repo — the longest lab instruction
is 255 characters, the longest question 327 — so they bound an abuser and are
unreachable by a learner. The test runs every lab step and all 692 catalogue
questions through them, so content authors find out in CI rather than in
production if that stops being true.

All three tutor routes now carry `requireSameSiteWrite`, the guard every
account and admin route already had: JSON body, `X-Study-Request: 1`, not
cross-site. A page on another origin can no longer drive this deployment's
upstream budget with a form post. `POST /api/admin/toggle-ai` and
`POST /api/admin/analyze` are mounted outside the admin router and were missing
that guard too; they have it now.

**This does not make the tutor routes authenticated, and that is deliberate.**
Anyone who can reach the port and set the header can still spend the Gemini
budget at 40 requests per 5 minutes per address. Requiring a session would
close it — and would take the tutor away from anyone studying without an
account, which the app offers on purpose ("Study on this device only"). That is
a product decision rather than a fix, so it is recorded in `docs/privacy.md`
instead of being made quietly here.

Four client call sites now send `X-Study-Request: 1`: `GeneralChat`,
`LabWalkthrough`, `PerformanceDashboard` and `useQuizEngine`. The change in
`useQuizEngine` is one header on an existing fetch and touches no grading logic.

## The rest of the leak audit

Checked and unchanged, because they were already right:

- `GET /api/account/me` and `PUT /api/account/progress` are keyed by the
  session cookie. A body that names another account is refused, not served, and
  the snapshot returned on a revision conflict is the caller's own.
- An anonymous `/me` returns `{username: null, isAdmin: false}` and nothing
  else; a refused progress write does not echo the username it was given.
- A signed-in learner who is not an administrator gets a flat 403 from the
  administrative routes with no detail.
- Nothing sent to Google carries a username, account id, session token or
  address. The upstream client is constructed with an API key and a fixed
  `User-Agent`.

`GET /api/admin/users` — every account with timestamps, to any administrator —
is the one real exposure of one person's data to another, and it is the subject
of the next release.

## Header and cookie claims

The README describes `HttpOnly`, `SameSite=Strict` and `Secure` cookies, and
`docs/privacy.md` now lists the header set. Both were checked against the
server and both hold. `server/leaks.test.ts` pins them against a real
production-mode response, including `Referrer-Policy: no-referrer` — without
which a link out of the app would tell the destination which page of the study
material the learner was on — and `Cache-Control: private, no-store` on account
responses, so a shared proxy cannot retain somebody's progress.

## Verification

- `npx vitest run` — 40 files, 351 tests. `server/accounts.test.ts` and
  `server/security.test.ts` are unchanged and pass, including the legacy
  migration case that recovers an account with an unsalted SHA-256 code.
- `npm run lint` and `npm run build` pass.
- Both new guards were checked by removing them: dropping the derivation floor
  fails the enumeration test, and the cross-site case fails without the header.
- No Docker on this machine; CI's container job covers the image.

No schema change. One behaviour change a client could notice: a tutor request
without `X-Study-Request: 1` now gets 403 instead of an answer. The app's own
four call sites send it, and this matches how `/api/account/*` has behaved for
several releases.
