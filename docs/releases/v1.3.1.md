# Version 1.3.1 — dependency, request and container hardening

A security and infrastructure pass over the deployed portal. No study content changes and no user-visible behaviour changes, other than the tutor rejecting an oversized question with a clear message.

- Production dependency advisories are down from 8 (3 high) to 2 moderate. The high-severity ones were `ip-address` (leading-zero octets decoded as decimal where resolvers decode them as octal, enabling SSRF and trust-boundary bypass), `browserslist` (unbounded memory growth to eventual OOM), and `nanoid` (infinite loop on a zero size). Fixed by `npm audit fix` within existing major versions; no application code changed.
- Express is switched to the built-in "simple" query parser. The two remaining advisories are both in `qs`, which Express 4 uses to parse query strings by default. No route in this app reads `req.query`, so the extended parser was attack surface with no corresponding feature; the reachable path is now gone. The advisories remain listed because the package is still in the dependency tree — resolving them at source means Express 5, which is a larger change than this release.
- The tutor endpoints bound their input. `/api/chat` is unauthenticated by design and forwards what it is given to a metered upstream; the 1mb body limit alone still allowed roughly a megabyte of prompt per request, leaving the rate limiter as the only cost control. Prompts are capped at 4000 characters and conversation history at 20 turns or 12000 characters, with a message telling the user what to change.
- The production container publishes its port on 127.0.0.1 rather than every interface. Published on 0.0.0.0 the app was reachable directly on the network, which bypasses whatever authentication the reverse proxy enforces, and — because `TRUSTED_PROXY_HOPS` is 1 in that deployment — let a direct client present its own `X-Forwarded-For` and so choose the address every rate limiter keys on. Set `WATCHGUARD_HOST_BIND=0.0.0.0` only for a deployment with no proxy in front, and set `TRUSTED_PROXY_HOPS=0` when you do.
- Both compose files set a memory and CPU ceiling on the container, defaulting to 512M and one core, with a 128M reservation. The portal is a single Node process over SQLite and sits well inside that; the limit exists so a defect cannot exhaust the Proxmox host. Raise it if the container is OOM-killed under real load rather than guessing upward.
- Proxy misconfiguration now announces itself. Getting `TRUSTED_PROXY_HOPS` wrong either collapses every client into one rate-limit bucket or makes the limiter spoofable, and previously did so silently in both directions. The first API request that disagrees with the configured value logs one warning naming the variable to change.
- The tutor input rules moved to `server/tutorInput.ts` with their own tests, so they can be exercised without importing `server.ts` and starting a listener.

Container resource limits and the loopback bind are exercised by `docker compose`, which the CI container job does not use — it runs `docker run` directly. Those two settings are verified by review and by YAML validation rather than by a test run, and should be confirmed on the host after deploying.

No SQLite migration, volume replacement, or topology v1 contract change is required. Keep the persistent data volume when deploying. If the portal is reached through Pangolin as intended, the loopback bind is transparent; if anything currently reaches the container directly by host address, it will stop working and should be moved behind the proxy. This branch is delivered by pull request; it does not merge or deploy itself.
