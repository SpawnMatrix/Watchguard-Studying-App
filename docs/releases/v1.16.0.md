# Version 1.16.0 — An inventory of what the portal records, and logs that cannot name anyone

This is the first of three releases doing a privacy pass over a portal that
holds real learner accounts. It covers two things: writing down what the app
actually records about people, and making sure the log cannot be one of those
things.

## docs/privacy.md

A new inventory, cited to file and line, of every place the app writes, stores
or transmits something about a learner: each log statement and what it can
contain, each table and how long it keeps its rows, each response body that
carries user data, and everything sent to Google when AI features are on.

Several entries are marked **Open** — things the inventory found and this
release does not change. They are in the document so that the next person
reads a list rather than rediscovers it:

- The study snapshot is not only a position in the material. It carries
  `quizStats.history`, which records the answers a learner selected, and
  `progress_backups` keeps up to 20 revisions of it. Weakness review and the
  spaced-repetition deck are built from exactly that history.
- There is no "delete my account" route.
- An *administrator* turns AI on for everybody; a learner has no per-person
  switch at the point of typing a question.
- The tutor routes need no account, so anyone who can reach the port can spend
  the deployment's Gemini budget.
- `recover()` skips key derivation when the username does not exist, so its
  response time distinguishes a real account from an invented one. `login()`
  gets this right; recovery does not.
- Whatever reverse proxy sits in front of this app keeps its own access log,
  and no change in this repo can turn that off.

The last two are fixed in the next release in this series.

## Logs

Every `console.*` call in `server.ts`, `server/` and `src/services/aiService.ts`
now goes through `server/log.ts`, which formats only values it constructed.

The risk was not the wording of the messages; it was the arguments. Four
handlers did `console.error("… API failed:", error)`. Node prints a thrown
object with its stack and its enumerable properties, and the call site cannot
see what those are — an HTTP client can attach the request it sent, a parser
can quote the text it choked on, and a stack frame can close over a prompt.

`logServerError` reduces any thrown value to `Class` or `Class(status|code)`:

```
[chat] failed: Error(429)
[ai-quiz] failed: TypeError
```

Nothing else survives. The class name and the code are filtered through a
character allow-list, because both are strings an attacker can influence in
principle, and anything unrecognised becomes `unknown`. Error messages are
dropped on purpose.

That costs something. A failure that used to be diagnosable from the log line
now has to be reproduced. The class and the HTTP status are kept because they
are what usually separates "the key is wrong" from "the network is down"; if
that turns out not to be enough, the answer is a reproduction, not a wider
formatter.

The four AI failures keep separate scopes (`ai-chat`, `ai-quiz`, `ai-lab`,
`ai-analysis`) so a log line still says which feature and which layer gave way.

## The test that keeps it true

`server/logging.test.ts` scans source rather than behaviour, in the style of
`src/engine/shortcuts.test.ts`. A `console.error(..., req.body)` added to a new
route next month would pass every behavioural test in this repo and still break
the promise.

It fails the build if a server file calls the console directly, or if a logging
call interpolates a request, an address, a username, a PIN, a recovery code, a
token, a cookie, question content, an answer, a prompt, a study snapshot, an
API key, an error `.message` or a `.stack`.

It strips comments and string literals first and checks only what is
interpolated. Without that step it would reject the existing proxy warning,
which explains in prose that a client can choose its own address — and worse,
it would teach maintainers to phrase warnings around a word list instead of
keeping values out of them. Two of its cases exist to stop it passing
vacuously: one plants a leak and expects the patterns to catch it, one asserts
the scan finds real call sites.

## Retention

`auth_failures` is the only place in the app that stores an IP address, and it
has to: rate limiting counts per source. What it did not do was forget.
`throttle()` prunes the buckets it touches, but only when somebody tries to
sign in, so the addresses from a burst of traffic sat in the table until the
next sign-in attempt — on a quiet portal, potentially weeks.

`AccountStore.pruneExpiredRecords()` now runs at startup and every five minutes
from `server.ts`, on an `unref`'d timer that never holds the process open. An
address now exists in the database for at most its own 15-minute window plus
five minutes, whether or not anyone signs in. The same sweep retires expired
and idle sessions and admin sessions instead of leaving the row until the next
sign-in.

Sessions written before the `last_seen` column existed carry `last_seen = 0`,
and `identify()` deliberately lets those run to their absolute expiry rather
than signing their owner out mid-upgrade. The sweep matches that, so upgrading
does not log anybody out.

## The dropped table

`auth_attempts` is the pre-hardening throttle table that `auth_failures`
replaced several releases ago. Nothing has written to it since, but rows from
that era still name accounts that failed to sign in, and no code path ever
expired them — a username could sit there indefinitely in a table the app no
longer reads.

The migration drops it (`PRAGMA user_version=3`), `clearThrottle` no longer
deletes from it, and `scripts/verify-backup.mjs` no longer requires it in a
backup. This is the first migration step in this app that removes something, so
to be explicit about the risk: it is a table with no readers and no writers, a
rollback to 1.15.5 recreates it empty via `CREATE TABLE IF NOT EXISTS`, and a
backup taken before this release still verifies.

## Verification

- `npx vitest run` — 39 files, 340 tests, all passing. `server/accounts.test.ts`
  and `server/security.test.ts` are unchanged and still pass, including the
  legacy-database migration case, which opens a pre-hardening database that has
  an `auth_attempts` table and a session row with `last_seen = 0`.
- Two assertions in `src/services/__tests__/aiService.test.ts` changed, and it
  is worth saying why rather than hiding it in the diff. They asserted
  `expect(errorSpy.mock.calls[0][1]).toBe("Simulated API failure")` — that is,
  they pinned the exact behaviour this release removes. The subject of those
  tests is the local fallback, which is untouched; the logging assertion now
  requires `[ai-quiz] failed: Error` **and** that the upstream message does not
  appear. That is a stronger assertion than the one it replaces.
- `npm run lint` and `npm run build` pass.
- The scanner was checked against a planted leak: adding `req.ip` to a real
  logging call in `server.ts` fails the suite, and restoring it passes.
- No Docker on this machine; CI's container job covers the image.

No route, response shape, cookie, schema column or client behaviour changes in
this release.
