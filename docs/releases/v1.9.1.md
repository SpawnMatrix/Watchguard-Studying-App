# Version 1.9.1 — Automated, verified database backups

The portal holds real learner accounts and progress, but backing them up has been a manual two-command procedure that nobody runs on a schedule. The data lives in a Docker volume that survives image updates and rollbacks, but not `docker compose down -v`, volume corruption, a bad restore, or losing the host.

This release adds an opt-in nightly backup job for the Docker host. **Nothing changes in production until an operator installs it.** The app, its image, Compose files and server are untouched.

## What it does

`deploy/docker/backup-watchguard.sh`, run daily at about 03:20 by `watchguard-backup.timer`:

1. **Waits for any deployment in progress, then holds the updater's lock,** so the auto-updater cannot replace the container halfway through a backup. The updater already skips a tick when that lock is busy.
2. **Takes a consistent copy** with `VACUUM INTO` inside the running container. This includes committed WAL data that a file copy would miss.
3. **Copies it to `/var/backups/watchguard-study/`** with owner-only permissions.
4. **Verifies the copy before trusting it,** using the Node runtime from the portal's own image in a throwaway container with no network and read-only mounts. No Node is needed on the host. `scripts/verify-backup.mjs` fails a backup that:
   - is empty or not a database
   - fails SQLite's integrity check
   - is missing any application table
   - contains no accounts, which is the dangerous case of a structurally perfect backup of an empty or reset database
5. **Only then prunes old backups:** files older than 30 days go, but the 7 newest are always kept. A rejected backup is renamed `.rejected`, nothing is pruned, and the job fails visibly in `systemctl --failed`.

Install steps, tuning variables, a manual verification command and a full restore procedure are in `docs/deployment-data.md`.

## Also

- `.gitattributes` forces LF line endings for shell scripts. A Windows checkout would otherwise write CRLF, which bash on the host cannot run.

## Verification

- 7 tests for the verifier cover a populated backup, an empty-but-valid one, row counts on failure, missing tables, a corrupt file, and zero-byte versus missing files.
- 8 contract tests for the host script check strict mode and locking, verify-before-prune ordering with the rejected-file exit, the accounts floor, the retention floor, that no Node is needed on the host, private file permissions, LF endings, and the timer and service wiring.
- The retention block was run against backdated files in four cases: all recent, mixed, all old above the floor, and all old below the floor. `bash -n` passes.
- I confirmed that `VACUUM INTO` writes a rollback-journal copy even from a WAL database, so it opens read-only without sidecar files.

This could not be run end to end with Docker in this environment. The first run on the host is the real test: `sudo systemctl start watchguard-backup.service` and check `journalctl -u watchguard-backup.service`.
