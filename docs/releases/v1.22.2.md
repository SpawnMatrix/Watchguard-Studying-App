# Version 1.22.2 — Settle the stranded branches, tag every release, tidy the root

Housekeeping from the 1.22.1 review: decide what to do with the two branches
that never became pull requests, give the repository the release tags it never
had, and remove files that described a project this no longer is.

## The two stranded branches

`codex/topology-ui-validation` (14 Sep) and `codex/modern-study-ui` (15 Sep)
were pushed but never opened as pull requests. The second contains the first.

**Ported:**

- Light-mode answer contrast, diagram markers and the legacy answer key, in
  1.22.1.
- **`MotionConfig reducedMotion="user"`**, here. `index.css` already cuts CSS
  animations under `prefers-reduced-motion`, but section changes and the
  profile dialog animate through `motion`, in JavaScript, where that CSS rule
  never applies. Someone who asked their operating system for less motion still
  got slides and fades on every navigation.
- **Accounts & tutor settings split into *Personal tutor* and *Administrator*
  views.** Every learner who opened the page saw an administrator password form
  beside their own tutor key. The page now opens on the tutor key. Both views
  stay mounted (`hidden`, not unmounted), so a half-typed key or password
  survives switching. The copy now drops "override administrator resource
  control gates" for what the key does. The card no longer lifts on hover,
  which suited a tile but not a page of form fields.

**Not ported:** the header redesign: account menu in a `<details>` popover,
new tagline, nav footer note, and horizontal nav auto-scroll. It was written
against `App.tsx` before What's New, Ideas and the privacy work changed the
header and navigation. Porting it would mean re-designing it, and at 375px the
navigation is now a grid, so the auto-scroll has nothing to scroll. If the
redesign is still wanted, it should start from today's header.

The branches themselves are left in place. Deleting remote branches cannot be
undone from this side, so that is the operator's call.

## Release tags

The repository had 32 versioned releases and no tags. Each historic release now
has an annotated `v<version>` tag on the commit that introduced it:
first-parent `main` for most, and the release commit inside the stack for
1.6.0–1.9.0 and 1.19.0. The tags were pushed together, and GitHub starts no
workflow when more than three tags arrive in one push, so `docker-publish.yml`
did not rebuild 32 old images.

`.github/workflows/tag-release.yml` keeps the tags current. On a push to `main`
that touches `package.json`, it tags the commit `v<version>` if no tag exists
yet, using the heading of the release notes as the message. A tag pushed with
`GITHUB_TOKEN` starts no other workflow, so the tag-triggered image publish
stays something a person does on purpose.

## Verification

- `npm run lint` clean. `npx vitest run`: green, including three new tests for
  the settings split: tutor view first, administrator view mounted but
  hidden, `aria-pressed` on the switch. `npm run build` clean.
  `check-release.mjs` passes against the parent branch and against
  `origin/main`.
- Tags: all 32 point at ancestors of `main`. Checked with
  `git merge-base --is-ancestor` before pushing, and `gh run list` showed no
  run triggered by the push.
- The tag workflow cannot run before it reaches `main`, so its first run is
  the merge of this release, which it should tag `v1.22.2`. **1.22.1 merges
  before the workflow exists and needs tagging by hand**, with the same
  command used for the history: `git tag -a v1.22.1 <merge commit>`.

Delivered by pull request, stacked on 1.22.1. No schema change, no new route,
and nothing that changes how the container is built or started.
