# Version 1.8.0 — Fix a broken network

The Topology Lab has a new mode: **Fix a broken network**. Every other exercise in the portal asks you to recognise an answer. A real ticket does not come with options: something is broken, a few things still work, and you have to find the wrong setting by testing and reading configuration. This mode gives you exactly that.

## How it works

1. **You get a help desk ticket.** For example: "PC-1 has a 169.254 address after a reboot. PC-2, which uses a static address, works normally."
2. **You get a generated branch office network** with one fault in it. The network has:
   - a Firebox with external, trusted and optional interfaces
   - an office switch with VLANs
   - a DHCP client PC and a static PC
   - a file server
   - a DMZ web server published with static NAT
   - a router to a lab network
3. **You run six connectivity tests** and open a trace for any that fail. A trace reads like a technician's view: routing decisions, ARP, and Traffic Monitor-style allow and deny lines, ending at the point where the traffic stops.
4. **You inspect any device and change its settings:**
   - host IP, prefix, gateway and DNS
   - switch port VLANs
   - Firebox policy order, enable state, ports and destinations
   - dynamic and static NAT
   - static routes
   - the DHCP scope and the options it hands out
5. **You re-run the tests.** Results that no longer match the configuration are flagged, so an old green tick is never mistaken for proof that a change worked.
6. **Once all six tests pass, you see the root cause** and why the symptoms looked the way they did. Up to three hints narrow things down from the symptoms, to the device, to the setting. "Show the fault" is there if you are stuck.

**No answer key.** Each test traces the packet through whatever the configuration currently says: addressing, VLANs, the route table, policies in order, NAT, and the return path. Any genuine fix passes. For a deny policy above an allow, for example, disabling it and moving it below both work. A careless change can break something that was working, just as it would on a live network.

## The faults

There are 17 fault types across four addressing plans, and the values are randomised within each:

- **Hosts:** wrong gateway, wrong mask, wrong DNS server
- **Switch:** a port in the wrong VLAN, either for a DHCP client or for a static host
- **Policies:** outbound HTTPS disabled, DNS allowed to the wrong server, a leftover deny above the allow, inbound policy on the wrong port
- **NAT:** dynamic NAT off, static NAT pointing at the wrong server
- **Routing:** a static route with the wrong gateway, and return-path faults on the web server and the lab server
- **DHCP:** a scope outside the subnet, the wrong DNS option, the wrong gateway option

These map to the NSE topics on policies, NAT, routing and network services, and to Network+ objectives 5.3 and 5.5.

## Verification

- **Simulation:** working networks pass all six tests across 200 seeds. Each fault breaks exactly its expected set of tests, checked across 40 seeds per fault. Random seeds reach every fault.
- **Fixes:** alternative valid fixes are accepted, plausible wrong fixes are rejected, and invalid input is handled without crashing.
- **UI:** a full scenario was played through in the browser. There is no horizontal overflow at 390px, and text contrast in light theme is 4.5:1 or better.

This is a teaching simulation of the behaviour the troubleshooting objectives rely on, not an emulator of Fireware. It needs no server, database or deployment change, and it works on every learning track.
