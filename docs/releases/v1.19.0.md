# Version 1.19.0 — An administrator can approve a recovery, and almost nothing else

Third and last of the privacy pass. 1.17.0 wrote the inventory, 1.18.0 fixed
the leaks it found, and this one shrinks what an administrator is able to see
and do.

## What is gone

`GET /api/admin/users` returned every account in the deployment — username,
sign-up time, progress revision, last activity — to any administrator, on every
console load. Nothing an administrator needs to do requires that, so it is
removed, along with `AccountStore.listAccounts()`. Nothing on the server can
produce a roster any more.

`POST /api/admin/users/sign-out` signed a named learner out of every device
without their involvement. That is not help; it is a capability over someone
else's session, and a reset the learner asked for already does it.

Both paths still answer, with 410 and no data, behind the same administrator
gate as before. Merging to `main` deploys within minutes, so there will be
browser tabs still running the previous console asking for `/users` on load,
and "this was removed" is a better answer for them — and for anyone scripting
against the API — than a bare 404 that reads like a bug. It also means
`server/security.test.ts` continues to pass unchanged, including its assertion
that an unauthenticated caller gets 403 there.

## What replaces it

### Assisted recovery, in three steps and two parties

1. The learner, on their own device, asks for help with their username.
   `POST /api/account/recovery/request` returns an eight-character code and
   sets a short-lived `wg_recovery` cookie that only that browser holds.
2. They read the code to an administrator, who approves that one code.
   `POST /api/admin/recovery/approve` tells the administrator nothing except
   whether the code is live — not the username, not when it was asked for, not
   whether the account has ever been used.
3. The learner sets the new PIN back on the device that asked.
   `POST /api/account/recovery/complete` needs the cookie from step 1.

So an approval is not a reset. An administrator holding a code cannot use it,
and a recovery cannot be done to somebody remotely without their device being
the one that starts and finishes it.

The code alphabet has no `0/O`, `1/I/L`, `5/S` or `8/B`, because somebody has
to read it aloud. Eight characters is about 38 bits; against a fifteen-minute
window and an administrator-only endpoint limited to 20 attempts per 15
minutes, it is not guessable. A request for a username that does not exist
still returns a code — one nothing can approve — so the endpoint cannot be
asked which accounts are real.

### Changing a PIN without anybody else

`POST /api/account/pin` changes a PIN from inside a signed-in session. The
commonest reason to ask for help is being signed in on a device and not
remembering the PIN, and that case should never involve an administrator. Every
session is retired and a fresh one issued, so a PIN change also evicts anyone
else signed in as that account. The recovery code is deliberately **not**
rotated: the learner may have written it down.

### What is recorded

That a recovery happened. A counter in `settings`, shown in the console so an
operator can notice recoveries happening more often than they remember helping
with. Not who asked, not when, not from where. The `recovery_requests` row
holds two digests, an account id and an expiry while the request is live, and
is deleted when it is spent, expires or is replaced.

## The part of this that does not work, stated plainly

The split stops an approval being useful to a *third party*. It does not stop
one person playing both parts: an administrator willing to impersonate a
learner can open a request for that username on their own machine, approve it
with their own session, and finish it there.

No server-side design fixes that without binding recovery to something only the
real owner holds, and there are only two candidates. One is the self-service
recovery code — which is already the no-administrator path, and is precisely
what this flow exists for people who have lost. The other is a durable
per-device identifier stored against the account, which is the kind of
per-person record this whole pass exists to avoid. Requiring two
administrators would also work, and would stop recovery working entirely on the
many deployments that have one.

`server/recovery.test.ts` asserts the limitation rather than only describing
it, so nobody later reads the two-party flow as a guarantee it does not make.
What the design does leave is evidence: a completed recovery destroys every
session on the account, rotates the recovery code, and moves the counter.

## The console

`AdminConsole.tsx` no longer fetches or renders a learner list. It has an
approval box, a role control that takes a typed username, the AI toggle, and
two counts. Role changes are typed rather than picked precisely because there
is no list to pick from.

`AccountGate.tsx` gains *Change my PIN* on the signed-in panel, and *Lost your
recovery code too?* on the sign-in screen. The assisted flow tracks which half
it is on separately from the code it is showing, so someone who reloads while
waiting for an administrator can come back and finish — asking again would
invalidate the approval they are waiting for.

## Schema

One additive migration, `PRAGMA user_version=4`:

```sql
CREATE TABLE IF NOT EXISTS recovery_requests (code_hash TEXT PRIMARY KEY,
  account_id INTEGER NOT NULL REFERENCES accounts(id), device_hash TEXT NOT NULL UNIQUE,
  approved INTEGER NOT NULL DEFAULT 0, expires_at INTEGER NOT NULL);
```

Nothing is rewritten or dropped. The retention sweep added in 1.17.0 prunes
expired requests along with everything else. A rollback to an earlier version
leaves the table in place and unread.

## Verification

- `npx vitest run` — 41 files, 371 tests. `server/accounts.test.ts` and
  `server/security.test.ts` pass **unchanged**.
- `npm run lint` and `npm run build` pass.
- Driven end to end against a production build on a scratch database:
  registered a bootstrap administrator, registered a learner, signed out, asked
  for a code through the UI, confirmed completion is refused with *"An
  administrator has not approved that code yet"* before approval, approved the
  code (typed sloppily, as `w9vg h98g`), completed on the same device, and
  landed signed in with a fresh recovery code and the old PIN rejected. Then
  changed a PIN from the signed-in panel and confirmed the previous one stops
  working. `/api/admin/users` answered 410; `/api/admin/me` carried no roster;
  the counter read 1.
- The whole of that session produced four server log lines, none naming anyone:
  the `ADMIN_PASSWORD` notice, the startup line, and two injected-env lines from
  dotenv.
- No Docker on this machine; CI's container job covers the image.

## Also found, not fixed

`src/index.css:1` imports web fonts from `fonts.googleapis.com`. The production
CSP blocks it, so no request reaches Google today and the portal renders in
system fonts — but the source intends to fetch from Google on every page load,
which would hand Google every visitor's address, and relaxing `style-src` later
would turn that on silently. Self-hosting the fonts or dropping the import
fixes it. Left alone here because `src/index.css` is where the theming work is.
