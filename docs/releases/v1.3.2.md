# Version 1.3.2 — restore proxy reachability

Hotfix. 1.3.1 bound the production container's published port to 127.0.0.1, and the portal went off the air: Pangolin reaches the app from its own network namespace rather than from the host loopback, so the proxy could no longer connect and every request returned Bad Gateway.

- The published port binds to all interfaces again by default. `WATCHGUARD_HOST_BIND` remains available, and is only correct when the reverse proxy shares this host's network namespace or is attached to the same container network.
- The container memory ceiling moves from 512M to 1G. It was not the cause of the outage, but a tight limit on a live service is a second way to fail and there was no measurement behind the original figure.

The exposure that 1.3.1 tried to close is real and remains open: with `TRUSTED_PROXY_HOPS` set, anything that reaches the published port directly can present its own `X-Forwarded-For` and choose the address the rate limiters key on. Close it at the host firewall, or attach Pangolin to this container's Docker network and then set `WATCHGUARD_HOST_BIND=127.0.0.1` — and confirm the portal still answers through the proxy before leaving it that way.

The lesson for the deployment notes: CI exercises the image with `docker run`, never with `docker compose`, so no automated check covers the published port, the resource limits, or anything else only Compose applies. A Compose-level change wants a deliberate check against the running proxy before it reaches main, because the auto-updater deploys `main` within five minutes.

No SQLite migration, volume replacement, or topology v1 contract change is required. Keep the persistent data volume when deploying.
