# Version 1.29.2 — A deploy updater that cleans up after itself

`deploy/docker/update-watchguard.sh` had three problems that only show on the
host, where nothing in CI runs it.

## What changed

- **Old images are removed.** Every deploy tags a new image with its commit,
  and the cleanup step, `docker image prune`, only removes untagged images. So
  every image ever deployed stayed on the disk. Every release also changes
  `package.json`, so each build reinstalls dependencies into fresh layers rather
  than reusing them. The updater now keeps the running image, the rollback
  target and the newest others up to `WATCHGUARD_KEEP_IMAGES` (default 3), and
  clears build cache unused for a week.
- **A commit that fails its health check is not retried every five minutes.**
  The updater rolled back but did not remember the failure, so the next tick
  deployed the same commit again. Each retry replaced the healthy container with
  the broken one for up to 90 seconds, until `main` moved. The commit is now
  recorded in `.failed-commit`. Each tick exits with an error naming it, so
  `systemctl --failed` shows that production is behind `main`. Delete the file
  to try again.
- **The checkout follows a rollback.** After rolling back, the checkout is reset
  to the previous commit, so the backup job and the next run read the Compose
  file and scripts that match the running container.
- **The database is backed up before each deploy**, while the old container is
  still serving, using the existing verified backup script.
  `WATCHGUARD_PREDEPLOY_BACKUP` is `true` by default (deploy even if the backup
  fails, which is no worse than before), `required`, or `false`.
  `backup-watchguard.sh` learned `WATCHGUARD_UPDATE_LOCK_HELD`. Without it, the
  backup would wait 15 minutes on the lock the updater already holds.
- `docs/deployment-data.md` names `/healthz` as the health check (it said
  `/api/session`) and documents all of the above, including how to reinstall
  the updater.

## Verification

- `scripts/updateScript.test.mjs` runs the real script under bash, with
  stand-in `docker`, `git` and `flock` commands that record what they were asked
  to do. It covers: first deploy; doing nothing when healthy; backup before
  `up`; rollback and the checkout reset; refusing to retry a failed commit;
  recovery when `main` moves; image retention (default and
  `WATCHGUARD_KEEP_IMAGES=2`); and the three backup modes. Six of the nine
  tests fail against the 1.28.2 script. One of those fails only because the old
  script cannot take its lock path from the environment.
- `npm run lint`, `npx vitest run` (60 files, 507 tests), `npm run build`, and `scripts/check-release.mjs` against the parent branch and `origin/main` all pass locally. CI's container job runs on the PR; no local Docker here.
- **Not verified on the host.** I have no access to the Proxmox container, so I
  have not seen how many images it actually holds or run this script there.
  `docker compose` itself is not exercised by any test.

## Deploy impact

None until it is installed. The updater runs from its installed copy at
`/usr/local/sbin/update-watchguard`, so merging this changes nothing on the host.
To adopt it, run the `install` command in
[What the updater does](../deployment-data.md#what-the-updater-does). The first
successful deploy after that removes old images. No database migration and no
change to the image, Compose files or server.
