# Version 1.24.0 — The sandbox remembers what you have solved

The Network Sandbox's six guided challenges were tracked in component state.
The counter said so honestly, "0 / 6 completed **this visit**", and it reset
on every reload, every tab switch that unmounted the section, and every new
device. Labs have kept step-level progress, synced with the account, since
1.7.0. The sandbox now does the same.

## How it is stored

- A new study key, **`watchguard-sandbox-progress-v1`**, holds the ids of the
  solved challenges in the order they were solved, for example
  `["udp","dns"]`. It is written when a challenge is completed and read when
  the sandbox opens.
- Because it is in `STUDY_KEYS`, it travels with the account snapshot like
  `watchguard-lab-progress-v1`: uploaded on change, restored at sign-in, and
  imported along with the rest of browser progress.
- **The server validates it** in the shared schema, `validSandboxProgress` in
  `src/engine/sandboxProgress.ts`. It must be an array of at most 64 distinct
  lowercase slugs of at most 32 characters. Anything else fails
  `validateSnapshot` with a 400, before it can replace a valid snapshot.
- The counter counts only challenges that still exist, so retiring or
  renaming a challenge later cannot leave someone at "7 / 6".
- The write happens in an effect, not inside the state updater. React may call
  an updater twice, and a storage write is a side effect.

The label is now "N / 6 completed", and the challenge picker marks solved
challenges with ✓. That marker existed before but was lost on every reload.

## A new privacy check

`docs/privacy.md` lists every key the portal stores. Adding a synced key is
exactly the kind of change that could slip past that inventory, so
`src/account/privacyInventory.test.ts` now fails if any entry in `STUDY_KEYS`
is missing from the document. The new key is listed there, with what it holds.

What it reveals is which of six practice exercises someone has solved, on the
same footing as lab progress. It carries no timestamps, unlike
`watchguard-study-progress-v1`'s answer history.

## Verification

- `npm run lint` clean. `npx vitest run`: 49 files, **436 tests**, green. New
  tests cover the validator (every real challenge id accepted, duplicates,
  capitals, spaces, over-long and over-many ids rejected), solve ordering, the
  count of existing challenges, the server snapshot accepting the key and
  rejecting three malformed forms, and the privacy inventory. `npm run build`
  clean.
- Driven in a production build: cleared the key, picked challenge 02, ran
  its flow, and saw "Challenge complete" and "1 / 6 completed" with `["udp"]`
  stored. After a full reload it still read 1 / 6, and the picker showed
  "✓ 02 / UDP is not always DNS".
- Account round trip on a scratch database: registered a throwaway account,
  PUT a snapshot with `["udp","dns"]` (200), had `["<img src=x>"]` rejected
  (400), signed out and back in, and got `["udp","dns"]` back.

Delivered by pull request, stacked on 1.23.0. No schema migration: the server
stores the snapshot as a whole, and an older snapshot without the key is
simply "nothing solved yet".
