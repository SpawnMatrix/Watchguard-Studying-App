# Version 1.3.3 — remove the container resource block

Second hotfix for the same outage. 1.3.2 restored the published port to all interfaces; the portal did not come back, so the remaining Compose-only change from 1.3.1 is removed as well.

The reasoning: the CI container job builds the real image and exercises it with `docker run`, and it passed on every one of these releases. The image starts, serves and passes the smoke test. So the failure is specific to what Compose applies on top, and after the port revert only one such change remained — the `deploy.resources` block added in 1.3.1.

- The `deploy:` block is removed from both Compose files, along with `WATCHGUARD_MEMORY_LIMIT` and `WATCHGUARD_CPU_LIMIT`.

A memory ceiling is still worth having, and it should return once it can be applied and verified against the running host rather than reasoned about from a machine with no container runtime. Restoring service comes first.

If the portal is still down after this deploys, the cause is not in the application repository: the image is known good from CI, and every Compose change made in 1.3.1 has now been reverted. Check the updater timer, the build output, and the host `.env` — in particular whether `WATCHGUARD_HOST_BIND` was copied from the 1.3.1 `.env.example`, which pinned it to `127.0.0.1`. A value set there overrides the default this release ships.

No SQLite migration, volume replacement, or topology v1 contract change is required. Keep the persistent data volume when deploying.
